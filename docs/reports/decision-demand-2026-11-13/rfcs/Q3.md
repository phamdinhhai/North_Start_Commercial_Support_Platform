# RFC Proposal Q3 — Work, Commitment, and External Expectation Semantics

**Status:** Proposal only — high-priority review question; not accepted.
**Owner:** Product + Data; Architecture owns lifecycle/audit; Security/Privacy reviews evidence access.

## Question
How should speaker, responsible party, origin, internal work, external expectation, acceptance, due/overdue, completion, and completion evidence be represented without treating an external action as verified?

## Canonical constraints
- Activity/NextAction/Commitment are named primitives, but full semantics remain under review.
- Buyer and seller commitments are examples, not permission to infer the responsible actor from speaker.
- Completion state and completion evidence must remain separate; observed message is not proof of the action it describes.
- Inferred changes require Commercial Event evidence/policy; AI remains draft-only (I-03/I-04).
- Important mutations are append-audited/reversible; UNKNOWN, absent, and conflicted remain visible (I-05/I-08/I-12).
- PM-1 permissions and CE-1 state semantics remain open.

## Alternatives
1. Retain one work construct but make speaker, responsible party, origin, execution status, due time, and completion evidence independent dimensions.
2. Separate internal work records from external expectations when shared lifecycle semantics mislead.
3. Keep one task-like construct only when external expectations are explicitly non-enforceable and evidence semantics are unambiguous.
4. Defer automated obligation/exception logic and use manual/synthetic records for validation only.

## Recommendation (proposal, not a decision)
Run a consented annotation set and workflow walkthrough covering mixed speaker/actor statements, explicit requests, promises, SLA work, AI suggestions, reassignment, late/off-system completion, cancellation, reminders, and no-observation cases. Prefer independent dimensions and separate external expectations if operators otherwise read overdue/completed as verified external failure/success. Keep current constructs as validation-only until accepted.

## Migration, security, and privacy impact
An accepted lifecycle affects work-item schemas, due-time ordering, reschedule/supersession, state transitions, API error contracts, queue views, audit, and existing pilot data. Message/evidence access must remain lead/workspace scoped and minimize/redact PII. Authorization must distinguish view, accept, and mutation; no privilege expansion follows from this proposal. No schema or automation change is authorized.

## Required approval
Product + Data + Architecture; Security/Privacy for message evidence and PM-1 capability changes. CE-1/CE-2 implications require their own approvals.

## Expiry / review
Review before freezing any obligation/next-action contract or exception automation, and by 2026-12-13. Manual/synthetic prototype may continue without treating this as resolved.

## Unresolved questions
- Is classification by speaker, expected actor, or both?
- What establishes acceptance/assignment of inferred or policy-created work?
- Does external “overdue” mean not observed, or an enforceable failure?
- Which evidence classes may close internal work and who may correct it?

## No-decision / no-go conditions
- **No decision:** unresolved party/status/evidence taxonomy, insufficient annotation agreement, or missing owner approval.
- **No-go:** completing external work without evidence, treating a message as action proof, collapsing declared/inferred/observed/absent/conflicted, or enabling autonomous mutation.
