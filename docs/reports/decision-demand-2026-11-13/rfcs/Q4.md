# RFC Proposal Q4 — Provenance and Time Semantics

**Status:** Proposal only — evaluation/data-contract review; not accepted.
**Owner:** Data + Engineering; Product owns interpretation; Architecture reviews contract impact.

## Question
What does `recorded_at` mean relative to asserted event time (`occurred_at`), source observation/capture (`captured_at`), adapter receipt/ingestion, and application assertion creation? How should V2 labels map without fabricating one canonical status or time?

## Canonical constraints
- Acquisition mode and assertion status are independent dimensions; confidence applies to inference only.
- Required provenance includes occurred/captured time, timezone, precision, source, evidence pointer/reason, version, actor, and correction lineage.
- Unknown, not observed, not requested, redacted, and not applicable are distinct; unknown event time must not be backfilled (I-08/I-12).
- Observed message does not prove the action described by that message.
- CE-2 scope remains open; evaluation labels do not decide CommercialEvent scope.

## Alternatives
1. Use canonical fields/statuses in production and map V2 labels only in evaluation reports.
2. Add a separately reviewed timestamp/provenance mapping contract if real cases show canonical fields insufficient.
3. Keep V2 labels research-only and report ambiguous mappings as UNKNOWN.
4. Add no new timestamp; preserve source timestamps plus adapter/application receipt metadata with explicit names.

## Recommendation (proposal, not a decision)
Use canonical provenance fields in production and document a report-only mapping table for V2 labels. Test imported, late, backdated, conflicting, timezone/precision-loss, absent-time, and message-versus-described-action cases. Preserve unknown event time and report late arrivals by event time without substituting capture/record time.

## Migration, security, and privacy impact
A contract change affects timestamp columns, parsers, idempotency comparisons, ordering, backfills, audit, exports, and report reproducibility. Source timestamps and evidence can contain PII; enforce access control, minimization, redaction, timezone/precision handling, retention, and immutable raw evidence. No timestamp backfill or canonical vocabulary change is authorized.

## Required approval
Data + Engineering + Product; Architecture if schemas/contracts change. Security/Privacy review is required for new evidence fields or retention paths. CE-2 approval remains separate.

## Expiry / review
Review before scoring time-sensitive V2 hypotheses and by 2026-12-13. Without approval, ambiguous labels remain research-only.

## Unresolved questions
- Is application assertion creation distinct from adapter ingestion for every source?
- Which report decisions require precision or intervals rather than instants?
- How should source clocks, timezone loss, and corrections be displayed?
- Which labels can be safely mapped to canonical acquisition/assertion dimensions?

## No-decision / no-go conditions
- **No decision:** missing concrete cases, unresolved timestamp ownership, or disagreement over unknown semantics.
- **No-go:** filling `occurred_at` from receipt time, treating label similarity as equivalence, collapsing acquisition mode with assertion status, or presenting claims as observed facts.
