## Architecture after current changes

```text
HTTP NestJS/Fastify (`src/main.ts`, `src/app.module.ts`)
  /health, /health/readiness (`src/api/health.controller.ts` + `infra/postgres/postgres-readiness.probe.ts`)
    — liveness vs bounded DB/migration readiness
  /v1/pilot/* (`src/api/pilot-loop.controller.ts` + `pilot-validation.ts`)
    → auth/RBAC ports bound to `infra/auth` and `infra/rbac` in `src/scripts/pilot-loop.module.ts`
    → `PilotLoopService` (`src/application/pilot/`) via ports and application policies
        → framework-independent `src/domain/{customer,lead,handoff,outcome,envelope,commercial-event,unknown-states}`
        → `ManualAdapter` (versioned, hashed raw envelope; workspace-scoped idempotency)
        → `PilotLoopStore` port (`src/ports/`)
            ├─ `PgPilotStore` (`src/infra/postgres/`) → Postgres transaction → migrations 001–007
            │   └─ 006 durable ingest command; 007 acquisition mode/source for evidence trust
            └─ `InMemoryPilotStore` (`src/infra/pilot/`) + `AuditStore` (explicit local/demo/test only)
  TelemetryService and FeedbackService (`src/infra/telemetry/`, `src/infra/feedback/`)
    → PostgreSQL tables; not wired as public product endpoints here
```

`src/scripts/pilot-loop.module.ts` chooses PostgreSQL in production/pilot and refuses silent memory fallback (`src/infra/postgres/postgres.service.ts`); local/demo/test memory must be explicitly selected without DB configuration. `src/api/health.controller.ts` exposes dependency-free liveness and readiness that checks PG and migration versions 001–005 in PG mode; memory readiness explicitly says `durable: false`. The `/v1/pilot` API provides scenario intake, lead read, handoff, accept, advance, complete, reschedule, external no-observation, outcome and audit history, with boundary input validation, typed 4xx refusals and scoped reads. `src/application/pilot/pilot-loop.service.ts` preserves an interim CE-1 state hypothesis, not a canonical transition table; inferred CommercialEvent modeling remains separate from manual assertion/audit. Source envelope and outcome assertions preserve explicit unknown/provenance rather than inventing attribution. The work-item axes are validation constructs, not newly canonical `Journey`, `Obligation`, `Contact`, or `Organization` entities.

**Important operational distinctions:** a recipient of an actionable item may view and accept that specific addressed work; view does not authorize complete/reschedule/stage/outcome. Mutations require current lead owner and, for item operations, the item's assigned actor. A superseded item refuses action and returns a replacement pointer. An intake/customer message is evidence that a message exists, **not** observed proof staff performed an action; `observed` completion requires a resolvable same-workspace, case-related action-evidence pointer and rejects intake/customer-authored evidence. Manual completion may be `declared`; inferred/absent/conflicted cannot close work, and an external obligation cannot be declared complete internally. `occurredAt='unknown'` is not silently replaced with record time. `PgPilotStore.save()` writes aggregate projection and audit in one transaction with optimistic version check. The PG read path and manual adapter are implementation boundaries; a test pass alone does not establish complete immutable evidence governance or commercial truth.

### Migration 005 — exact contract, not a cleanup verdict

Files: `product/migrations/005_workspace_consistency.up.sql`, `.down.sql`; conditional test: `product/src/infra/postgres/migration-005.integration.spec.ts` (four tests **skipped in this run**). Up creates `workspace_consistency_quarantine` keyed by `(source_table, source_id)` and **copies JSONB snapshots** of existing contradictions for `commercial_event`, `handoff`, `pilot_work_item`, `outcome`, linked `feedback`, and `audit_record` where `entity_type='lead'`. It does **not** remove, rewrite, or infer workspace for live historical rows. A uniqueness constraint on `(lead.id, lead.workspace_id)` supports five `(lead_id, workspace_id)` composite FKs `NOT VALID`: new/changed typed child references are checked, old contradictions remain unvalidated/live. Feedback may have null lead; on lead deletion only `feedback.lead_id` is set null, retaining its workspace and row (requires PostgreSQL support for column-list `SET NULL`, targeted by PG16 test). A lead-audit trigger rejects malformed, missing, or cross-workspace lead references on insert or updates to identity fields; audit of other entity types stays polymorphic and unverified by this trigger. Down drops those constraints/function/trigger/parent unique key but **retains quarantine snapshots**; reapplication can add additional snapshot rows. `ON CONFLICT DO NOTHING` preserves the first snapshot, so it is inspection evidence, not a guaranteed current-state mirror.

Limitations: no `VALIDATE CONSTRAINT`, no remediation, no proof legacy contradictory rows cannot be read through other paths; orphan cases in typed tables are bounded by existing single-column FKs, while polymorphic audit requires separate governance. A down migration reopens future-write inconsistency and is not backup/restore. The migration 005 tests create a temporary PG database only when `TEST_DATABASE_URL` is set; their assertions cover live-row retention, quarantine, fresh-write rejection, feedback delete behavior, down/reapply. They have **not been executed in this fresh verification**, and production data shape, migration locks/timing, downstream readers and deployment are unknown.

## Technical baseline vs commercial readiness

The current tree has a typechecked/linted/built manual pilot backend with 267 passing non-PG tests and three memory-mode health E2E checks. That is a **technical development baseline**, subject to the explicit PG/CI gaps above. It is **not** evidence of repeatable clean install, deployability, real tenant security, commercial adoption, measurable revenue uplift, accurate attribution, or a usable Sales/Manager product. The North Star five engines, service-model control plane/customer-hosted packaging, full Pancake/CRM adapters, real AI, and revenue-credit rules are not shipped by this baseline. Product learning gates require external users, defined measurement and evidence; green source tests cannot replace customer validation.
