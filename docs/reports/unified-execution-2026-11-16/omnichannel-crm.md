## Decision

Keep the platform's lead, handoff, obligation, evidence and outcome semantics independent. An inbox being resolved does not complete an outstanding commercial obligation. A CRM contact ID is an external reference, never canonical Customer or immutable acquisition-episode Lead identity.

Read authority: `AGENTS.md`; canonical `PRODUCT_CONSTITUTION.md`, `ARCHITECTURE_CONSTITUTION.md`, `DOMAIN_INVARIANTS.md`, `OPEN_DECISIONS.md`; current operator client and pilot service; `architecture-baseline.md`. The current product promise is evidence-backed handoff and next action, not rebuilding an omnichannel inbox. I-01/02/03/05/07/08/09/10/11/12 remain constraints. ID-1 merge policy, ID-2 CRM field mapping and PM-1 capabilities remain OPEN; CE-1/CE-2/MM-1/LG-1 are not resolved by these comparisons.

### Chatwoot: assignment is conversation operations

Read `app/services/conversations/assignment_service.rb`, functions `perform`, `assign_agent`, `assign_ai_assignee`, `assignee`, `agent_bot`; `app/policies/conversation_policy.rb`, `show?`, `inbox_access?`, `team_access?`; and `spec/services/conversations/assignment_service_spec.rb` through human/bot assignment cases. Assignment uses a conversation row lock; user lookup is account-scoped and bot lookup uses account accessibility. Assigning a human clears AI ownership; a bot-owned pending conversation opens and starts waiting time, while ordinary reassignment can preserve resolved status. Tests explicitly cover those distinctions and administrator takeover.

This offers useful evidence that assignment and resolution are independent even within an inbox. It is not the platform's Sales acceptance contract. Its inbox-or-team conversation read policy is incompatible with copying I-09 authorization wholesale. No connector delivery retry guarantee was established from this service. Provider assignment documentation confirms the account/conversation assignment endpoint and agent/team inputs, not internal Lead permissions: [official assignment API](https://developers.chatwoot.com/api-reference/conversation-assignments/assign-conversation).

### Twenty: generated workspace schema is a mapping input

Read `packages/twenty-server/src/engine/guards/workspace-not-suspended.guard.ts` (`canActivate`, `isAllowedWhenSuspended`), its `__tests__/workspace-not-suspended.guard.spec.ts`, and `packages/twenty-server/test/integration/graphql/suites/object-generated/tasks.integration-spec.ts`. The latter queries task title, body, dueAt, status, assigneeId and timestamps with an admin fixture bearer token; it checks response shape, not our lead-scoped denial or completion-evidence contract. The guard checks workspace suspension with an explicit metadata exception; it does not independently prove tenant or record isolation.

[Official API documentation](https://docs.twenty.com/developers/extend/api) describes REST/GraphQL generated per workspace, separate core and metadata APIs, bearer API keys and role scoping. Therefore an adapter spike must record the actual workspace schema/version and credential scope; a static guessed Person-to-Customer or Opportunity-to-Lead map is not authorized (ID-2). Connector retry and conflict behavior were not established in this bounded server review. REFERENCE metadata inspection; do not let remote schema changes mutate core meaning.

### Frappe CRM: tasks have explicit assignee and record reference

Read `crm/fcrm/doctype/crm_task/crm_task.py` (`after_insert`, `validate`, `assign_to`, `unassign_from_previous_user`, `set_all_day_due_date`, `default_list_data`), matching `test_crm_task.py`, task JSON permissions, and the initial validation/ownership section of `crm_lead.py`. Task columns include status, priority, due date, assigned user and last modified; references are doctype+document name. Tests assert exact assignment, reassignment removing the previous user, reference linkage and basic task creation. All-day date normalization is explicit, a useful reminder to distinguish dates from timestamps.

Lead validation may share with a new owner, assign the owner, log status change and trigger background enrichment. Those are provider semantics, not approved platform permissions or an evidence pipeline. Task role rows permit Sales User/Manager actions but do not establish the complete framework permission chain or multi-tenant isolation. Frappe framework authentication, site tenancy and connector retries were not audited here. [Official assignment-rule page](https://docs.frappe.io/crm/assignment-rule) is reference context only; no live assignment was exercised. ADAPT presentation/test cases; do not import status enums, owner-sharing or auto-enrichment.

### HubSpot: SDK transport is not business authority

Read `src/client.ts` (`Client`, `init`, discovery getters), `src/services/decorators/RetryDecorator.ts` (`decorate`, `_waitAfterRequestFailure`), `test/spec/crm/contacts/contacts.spec.ts` and `test/unit/httpTransport.spec.ts`. Contacts tests prove SDK discovery wiring, not provider access. Transport tests use a local HTTP server and assert bearer authorization and JSON request bodies. Retry decorator bounds attempts by configured count, retries 5xx with linear waits and selected 429 policy/message cases; it is not a universal Retry-After parser or idempotency protocol. `Client.init` installs decorators via a singleton service: verify cross-client configuration isolation before adopting in a multi-connection process.

Credentials select provider access; SDK use does not supply our workspace+lead authorization or field authority. [Official error guidance](https://developers.hubspot.com/docs/api-reference/error-handling) must be consulted for the actual API/version when implementing. Preserve correlation/error metadata without raw tokens/PII, retry only safe/idempotent adapter operations, bound each connection and retain dead-letter inspection. A successfully updated remote contact/task is external observation, not canonical Won/revenue or a completed obligation.

## Domain and integration contract to preserve

Keep provider connection + account/tenant + object type + external ID as namespaced references; store immutable raw envelopes and versioned mappings separately. Preserve source timestamp, captured timestamp and unknown occurrence time. Never join by display name/email alone. Customer != Lead; contact ID != either canonical ID. ID-1 prevents automatic dedup/merge; ID-2 requires a reviewed mapping before production field ownership or bidirectional sync. For each proposed field record provider observation, canonical authority, evidence basis, mapping version and conflict disposition; unresolved authority remains UNKNOWN, not last-writer-wins.

External owner/team, inbox resolved, CRM task Done, remote deal Won, webhook received and HTTP success are separate facts. None alone authorizes canonical ownership transfer, completion, commercial transition, outcome or revenue attribution. AI can draft handoff context with inspectable evidence; only approved human/policy commands through the existing evidence/audit boundary can mutate. No new CE scope or state graph is proposed.

For a later adapter spike, prove tenant/account mismatch rejection, least-privilege credential handling, cross-lead denial, replay idempotency, safe retry/dead-letter behavior, remote rename/deletion and schema drift, out-of-order delivery, conflict and correction provenance. Source tests in third-party projects do not replace these platform contract tests.
